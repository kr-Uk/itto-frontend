# 스침 판정 배치 구현
> 날짜: 2026-02-19

## 작업 요약
- 기능명세서의 핵심 매칭 로직인 "스침 판정 배치"를 Spring @Scheduled + Redis 기반으로 구현
- 5분 주기로 같은 H3 셀 내 사용자 페어를 추출하고, 거리/차단/필터 조건을 확인하여 관계(우연/필연)를 자동 생성
- 만료 처리 배치(30분 주기)로 PILYEON/INYEON/PAST 상태 자동 전이

## 핵심 개념 설명

### @Scheduled vs Spring Batch
- **Spring Batch**: 대량 데이터 ETL에 적합한 프레임워크 (Job → Step → Reader/Processor/Writer)
- **@Scheduled**: 단순 주기 실행에 적합. 별도 의존성 없이 Spring Boot 기본 제공
- **선택 이유**: 스침 판정은 Redis 데이터 기반의 간단한 반복 작업이라 @Scheduled이 적절. Spring Batch의 복잡한 인프라(JobRepository, meta-data 테이블 등)가 불필요

### Redis 위치 데이터 구조
```
location:user:{userId}     → Hash {h3Index, lat, lng}   TTL=10분
location:h3:{h3Index}      → Set<userId>                 TTL=10분
encounter:cooldown:{min}:{max} → "1"                     TTL=30분
```
- **Hash**: 사용자별 현재 위치 저장. H3 셀이 바뀌면 이전 셀의 Set에서 제거
- **Set**: H3 셀별 사용자 목록. 배치에서 같은 셀 내 사용자 페어를 효율적으로 추출
- **쿨다운**: 동일 페어의 연속 스침 방지 (30분)

### H3 헥사곤 시스템
- Resolution 9 사용 (~100m 변 길이, ~105,332m² 면적)
- 같은 H3 셀에 있으면 1차 필터 통과 → Haversine으로 정밀 거리 계산 (200m 이내)
- `h3.latLngToCellAddress(lat, lng, 9)`로 좌표 → H3 인덱스 변환

### 관계 상태 머신
```
스침 1회 → UYEON (우연, 무기한)
스침 2회 → PILYEON (필연, 24시간 타이머)
필연 만료 → PAST (지난인연, 7일)
지난인연 만료 → ENDED (종료)
종료 + 재스침 → UYEON (재시작)
```

## 코드 설명

### 1. 위치 데이터 Redis 저장 (LocationService)
```java
private void saveLocationToRedis(Long userId, String h3Index, double lat, double lng) {
    String userKey = LOCATION_USER_PREFIX + userId;
    String h3Key = LOCATION_H3_PREFIX + h3Index;

    // 이전 H3 셀에서 제거 (셀이 바뀐 경우)
    String prevH3 = (String) redisTemplate.opsForHash().get(userKey, "h3Index");
    if (prevH3 != null && !prevH3.equals(h3Index)) {
        redisTemplate.opsForSet().remove(LOCATION_H3_PREFIX + prevH3, userId.toString());
    }

    // 사용자 위치 Hash + H3 셀 Set 갱신
    redisTemplate.opsForHash().put(userKey, "h3Index", h3Index);
    redisTemplate.opsForHash().put(userKey, "lat", String.valueOf(lat));
    redisTemplate.opsForHash().put(userKey, "lng", String.valueOf(lng));
    redisTemplate.expire(userKey, LOCATION_TTL);
    redisTemplate.opsForSet().add(h3Key, userId.toString());
    redisTemplate.expire(h3Key, LOCATION_TTL);
}
```
- **핵심**: 사용자가 H3 셀을 이동하면 이전 셀의 Set에서 자동 제거
- **TTL 10분**: 위치 전송이 끊기면 자연스럽게 매칭 대상에서 제외

### 2. 스침 판정 메인 로직 (EncounterBatchService.detectEncounters)
```java
// Redis SCAN으로 활성 H3 셀 수집
Set<String> h3Keys = scanRedisKeys("location:h3:*");

for (String h3Key : h3Keys) {
    Set<String> userIdStrings = redisTemplate.opsForSet().members(h3Key);
    // 2명 이상이어야 스침 가능
    if (userIdStrings.size() < 2) continue;

    // 제외 지역 필터링 → 사용자 페어별 판정
    processUserPairs(userIds, h3Index, batchWindow);
}
```

### 3. 필터링 체인 (processEncounterPair)
```
쿨다운 체크 → 차단 체크 → 사용자 유효성 → 매칭 설정 → 기존 관계 → 거리 계산
```
- 6단계 필터를 순서대로 적용하여 불필요한 DB 조회를 최소화
- 비용이 낮은 체크(Redis 쿨다운)를 먼저, 비용이 높은 체크(DB 조회)를 나중에

### 4. Haversine 거리 공식
```java
double dLat = Math.toRadians(lat2 - lat1);
double dLon = Math.toRadians(lon2 - lon1);
double a = sin(dLat/2)² + cos(lat1) * cos(lat2) * sin(dLon/2)²;
double c = 2 * atan2(√a, √(1-a));
distance = R * c;  // R = 6,371,000m (지구 반지름)
```
- GPS 좌표 간 실제 지표면 거리를 계산하는 공식
- 200m 이내일 때만 스침으로 판정

## 새로 배울 수 있는 것
- **Redis 자료구조 설계**: Hash와 Set을 조합하여 위치 기반 조회를 효율적으로 구현하는 방법
- **@Scheduled 스케줄러**: Spring Boot에서 주기적 작업을 설정하는 간단한 방법 (fixedRate, initialDelay)
- **H3 공간 인덱싱**: Uber의 H3 시스템으로 GPS 좌표를 헥사곤 셀로 변환하여 근접 검색을 O(1)로 수행
- **상태 머신 패턴**: 엔티티의 상태 전이를 명시적 메서드로 관리하여 비즈니스 규칙을 보장
- **Redis SCAN vs KEYS**: 프로덕션에서는 KEYS 대신 SCAN을 사용하여 Redis 블로킹을 방지

## 리스크 및 주의사항
- **단일 서버 전제**: @Scheduled는 서버 인스턴스별로 실행됨. 다중 서버 환경에서는 ShedLock 또는 Redis 분산 락 필요
- **Redis 데이터 유실**: Redis 재시작 시 위치 데이터가 소실됨 (TTL 10분이라 빠르게 복구)
- **대규모 트래픽**: 사용자가 많아지면 H3 셀당 사용자 수가 증가하여 N² 페어 연산 비용 증가 → 셀 분할 또는 배치 분산 필요
- **쿨다운 30분**: 동일 장소에서 30분 이내 재스침은 무시됨. 값을 조정하려면 `COOLDOWN_MINUTES` 상수 변경
- **거리 임계값 200m**: `ENCOUNTER_DISTANCE_METERS` 상수로 조정 가능. H3 Resolution 9 셀 크기(~200m 직경)와 맞춤
