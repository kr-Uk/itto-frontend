## 핵심 개념 설명

### MVP (Minimum Viable Product)
최소 기능 제품. 핵심 사용자 경험을 검증할 수 있는 최소한의 기능만 구현된 버전.
Itto의 MVP 핵심 흐름: 회원가입 → 위치 수집 → 스침 판정 → 인연 → 채팅

### 상태 머신 (State Machine)
엔티티가 가질 수 있는 상태와 전이 규칙을 정의한 패턴.
Itto의 관계 상태: UYEON → PILYEON → PENDING → INYEON → PAST → ENDED
각 전이에는 트리거(스침, 신청, 만료 등)와 타이머(24h, 7d)가 정의됨.

### 영수증 검증 (Receipt Validation)
인앱결제 보안의 핵심. 클라이언트가 보낸 구매 영수증을 서버에서 Apple/Google API로 검증.
현재 stub(항상 성공)이므로 가짜 영수증으로 무제한 매듭 획득 가능.

## 백엔드 분석 결과

### 치명적 이슈 (즉시 수정 필요)
1. **영수증 검증 stub**: `ReceiptValidationService`가 항상 `isValid=true` 반환
2. **월 무료 횟수 미차감**: `RelationshipService.requestInyeon`에서 MonthlyUsage 업데이트 없음

### 중요 이슈 (베타 전 수정 권장)
3. **매듭 음수 가능**: `User.deductKnots`에 잔액 체크 없음
4. **Relationship 중복 race condition**: DB constraint로 데이터 무결성은 보호되나 배치 오류 발생 가능
5. **닉네임 중복 체크 누락**: `SignupService.saveProfile`에서 검증 없음

### 긍정적 발견
- Relationship unique constraint + CHECK(user_id_1 < user_id_2) 완벽
- 차단 양방향 체크 빈틈없음
- 관계 상태 전이가 기능명세서와 100% 일치
- FCM 푸시 실제 구현 (stub 아님)
- Redis SCAN 패턴 안전
- 소프트 딜리트 정상 구현

## 새로 배울 수 있는 것
- **MVP 점검 방법론**: 기능명세서 기준으로 코드를 섹션별 매핑하여 완성도를 정량화
- **영수증 검증의 중요성**: 서버 측 검증 없이는 클라이언트 조작으로 무제한 구매 가능
- **동시성 분석**: SELECT → INSERT 패턴에서 race condition 발생 가능성과 DB constraint의 보호 역할
- **상태 머신 검증**: 모든 상태 전이 경로를 매핑하여 누락/오류를 체계적으로 검출

## 리스크 및 주의사항
- 결제 관련 이슈(영수증 검증, 무료 횟수)는 MVP 출시 전 반드시 해결해야 함
- 동시성 이슈는 사용자가 적은 초기에는 문제 안 되지만 스케일업 시 반드시 해결 필요
- 프론트엔드는 거의 완성 상태로 UI 폴리싱 단계에 진입 가능
